# 真太阳时计算与验证

真太阳时由本地程序计算，不需要在线排盘。`options.time_basis` 默认 `clock`；选择 `true_solar` 后，八字日柱和时柱使用出生地真太阳钟面日期时间。出生年月柱和起运使用真实出生瞬间，紫微使用出生地钟表日期时间。两套时间分别保存，避免把太阳钟面重新解释为时区时间。

## 输入与公式

birth.time 始终填写原始钟表记录，birth.timezone 填实际 IANA 时区或已核实的 UTC 偏移。birth.longitude 为数字，东经正、西经负，范围 −180 至 180；可填写 longitude_source 记录用户提供、地图链接及坐标精度。没有经度时使用 clock，不根据模型记忆补城市坐标。城市中心与具体出生地点有区别；经度每差 0.25°，时间修正差 1 分钟，靠近边界时需要更精确地点。

```
总修正分钟 = 4 × 东经度 − 出生时实际 UTC 偏移分钟 + 均时差分钟
地方平太阳时 = 原始钟表日期时间 + 经度与时区修正
地方真太阳时 = 地方平太阳时 + 均时差
```

均时差采用 [NOAA 太阳计算器](https://gml.noaa.gov/grad/solcalc/calcdetails.html)的 Meeus 太阳位置公式，使用出生 UTC 瞬间的完整儒略日，方法编号 `noaa-meeus-equation-of-time/v1`。具体计算见 [solar-time.cjs](../scripts/solar-time.cjs)。[NOAA 简式公式](https://gml.noaa.gov/grad/solcalc/solareqns.PDF)说明了均时差、经度与时区的组合关系；本实现采用完整太阳位置函数，不使用其日序 Fourier 近似代替。

实际偏移包含历史夏令时。例如 1990-05-20 14:30、Asia/Shanghai、经度 116.4°，实际偏移 +09:00：经度/时区修正 −74.4 分，均时差约 +3.536733 分，总修正约 −70.863267 分，太阳钟面为 13:19:08.203；UTC 保持 05:30Z。不能再额外减去一次夏令时。

仅紫微模式不接受 true_solar；both 模式支持“八字太阳时、紫微钟表时”。六爻占时规则独立，未增加太阳时选项。已经手工校正的太阳时不能再当作原始出生钟表时间输入。

## 输出与复核

`normalized.solar_time` 保存经度、UTC 瞬间、实际偏移、经度修正、均时差、总修正、平/真太阳时及跨日标记。提供经度但选择 clock 时也计算校正结果供对照，所选口径保持 clock。

`bazi.chart.time_validation`（BZ-TIME-CHECK）同时保存钟表与太阳时的日柱/时柱，标记 day_changes / hour_changes。`day_hour_calculation_datetime` 是本次实际采用的钟面时间。中间计算保留亚秒精度，展示毫秒按向下取整；时辰按实际校正结果判定。

太阳钟面距午夜或时辰边界在 60 秒内时，`within_60_second_review_band=true`。年/月柱另有 `jieqi_boundary_review`（BZ-JIE-REVIEW），按实际出生瞬间检查十二节边界。这是样本结果支持的复核策略，不是所有日期的天文误差上限。用户记录有更大误差时按实际误差扩大候选范围。

出生范围仍填写钟表时间。时辰对照程序将太阳时的日期、早晚子与各时辰边界反算回钟表秒，和紫微钟表边界、节气及 DST 边界一起分段；不能只在原钟表时辰取样后假定太阳时结构不变。未知全天会增加候选点，最多 256 点。每个候选保留真太阳时读数和实际使用读数。

聊天只在时间校正改变判断或靠近边界时自然说明，例如“校正后是辰时，这次八字按辰时看；紫微沿用出生记录的巳时”。无需每次重述方法。详细过程或文件报告只在用户需要时展示。

## 独立验证资料

- [NOAA 向量](verification/noaa-solar-fixtures.json)：用下载的原始 main.js 数学函数生成 1900–2100 每月 1 点，共 2412 点；另有 18 个地点/时区案例。固定源码 SHA-256，测试误差小于 10⁻⁹ 分钟。这验证公式移植的一致性，不将浮点吻合等同于观测精度。
- [寿星历向量](verification/sxtwl-bazi-fixtures.json)：独立 sxtwl 2.0.7 生成 430 组四柱、起运方向和分钟差，以及 91 个十二节时刻。真太阳钟面输入来自独立 NOAA 函数，年月使用原始实际瞬间对应的北京日期。
- [交叉结果](verification/cross-check-results.json)：430 组四柱和顺逆一致；91 个节气最大差约 54.407 秒；起运原始分钟差最大相差 1 分钟。起运算法中 1 分钟可对应 2 小时起运偏移，因此临界例不能把两套历法当作完全同值。

寿星历 getYearGZ/getMonthGZ 是日级接口，四柱交叉样本避免节气切换日；节气瞬间单独使用其 JD 数据检查。2024 立春：寿星历约 16:26:53.122，本包固定历法 16:27:07，差约 13.878 秒；这段区间两套历法会给不同年月柱，应复核边界两侧，不强行判为一致。

这些 JSON 和测试均随技能携带，手机使用 Node 执行测试即可，不需要 Python 或 C++。生成参考数据的验证环境不进入安装包。跨项目采用范围与子平口径见 [八字理论核对](bazi-theory-audit.md)。
